# 创作者案例：从选题到采用，不把中间状态混成成果

这是一个全虚构的工作流演练，没有真实广告、收入、作品或发布回执。

从 `vault-template/02-项目/创作者示例/当前状态.md` 开始。四份笔记分别承担当前入口、采用决定、素材许可和内容链路；不需要新建第二套任务系统。

## 场景一：写稿之前

先写“观众真正担心什么”，再写软件功能。本例的潜在需求是：**已经投入的思考和项目积累，不因换 AI 工具就难以接续**。封面可以表达“给 AI 装个记忆库”，正文则必须解释本地文件、按需读取和交接边界，不能承诺所有 AI 自动共享全部记忆。

“有人用学钢琴与孩子成长结果的关系做营销”可以帮助理解从功能走向深层需求；没有原始出处时，只作为使用者提供的类比，不把某国广告史或教育效果当已核实事实。吸引力不能建立在不成立的因果或夸大承诺上。

## 场景二：资料与画面

先用 [网页捕获](web-capture.md) 留下来源，再写自己的解释。把录屏对应到实际台词；视觉示意与真实界面明确区分。软件版本和测试日期留在资料里，避免旧教程覆盖新事实。

可以用 Canvas 把“痛点 → 承诺 → 真实演示 → 原理 → 限制 → 下一步”排成图。这个库不依赖社区绘图插件；确需手绘时再单独选型。

## 场景三：换一个助手

执行 [跨 AI 交接演练](cross-ai-handover.md)，让新助手先回述三份必要资料。检查它有没有误把“考虑换 AI 旁白”当采用决定，或把“音乐已下载”说成可商用。

## 场景四：审片与结案

实际反馈应包含版本、时间点、反馈者、修改或采用决定。源视频、成片、字幕、工程与授权证据在各自目录保存，笔记主要存路径和关系，不把所有大媒体复制进库。

只有本人明确采用，才把候选改为采用；只有有平台回执，才记录发布；只有有真实后台或结算，才填写收入。每个结论链接证据，未知值不填成 0。

## 练习完成标准

1. 能在唯一当前入口找到进度、采用决定、未知与下一步。
2. 能从稿件追到公开资料，从素材追到许可缺口。
3. 新助手只读选定包就能通过五项交接检查，不能假装知道未提供历史。
4. 没有重复待办、虚构成绩、自动发布或未授权外发。

这些是验收标准，不是仓库替你做完了一条真实视频的承诺。
